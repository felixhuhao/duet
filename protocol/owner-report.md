# Owner 汇报协议

> Goal v1：每个 Goal 在 DEV_DONE 生成结构化 Completion Package；是否立即推送、每日汇总或累计
> 若干 Goal 汇总由 owner 指定。目标不是增加汇报频率，而是让 owner 用一屏看懂结果与决策点。

## 与 peer 门铃的边界

- **peer 门铃**只负责唤醒和路由：路径、轮次、verdict；不复制工件内容；
- **owner 汇报**负责信息压缩和注意力路由：是已提交工件的摘要投影，不是第二真源；
- 汇报正文由 agent 在当前 turn 末尾输出；system notification 只提醒事件和真源路径，不能替代正文；
- 仍然事件驱动：只在 owner 指定摘要点、gate、incident、有意义状态变化或 owner 主动询问时汇报，
  不新增 heartbeat、定时 ping 或 orchestrator 常驻；
- 汇报中的状态、读数、commit 和判断必须能回链到工作仓真源。

## 通用格式

```text
【<Goal>｜<一句话状态>】

结论：当前结果、所处阶段，以及是否按计划推进。
完成及影响：本轮最重要的 1～3 项，以及它们让产品、计划或风险发生了什么变化。
发现及意义：新事实、风险或与原计划不同之处，并解释“所以怎样”；没有则写“无新增风险”。
需拍板：无；或一句话题面 + 选项代价 + 推荐，并说明阻塞/不阻塞什么。
下一步：承担者 + 动作 + 下一次交棒或完成条件。

可选·值得看：只有确实需要 owner 亲自判断时才写，说明看什么、为什么、要判断什么。
可选·证据：commit、关键门禁读数、真源路径；统一放末尾，默认最多两个引用。
```

正文五项必须自含：**删除所有链接后，owner 仍能理解做了什么、意味着什么并完成决策**。
字段可以合并成短段，但不得省略“需拍板”和“下一步”。首次出现 Goal、finding、watchlist
等编号时，必须跟一句人话自述。

## 常见变体

### Milestone / 旁观通报

结论先说阶段是否完成；完成及影响、发现及意义、下一步为必填。无需 owner 动作时明确写
“需拍板：无”，不得用疑问句把执行权递回 owner。外部依赖只报 parked 项、唯一唤醒事件和
`pair available`，不能把“等待 X”写成 pair 的工作。

### Decision / Gate

开头三项依次是：①一句话说清拍什么；②选项、代价与推荐；③阻塞项与非阻塞项。
owner 应能只回 `A`、`B`、`ack` 或一句修正意见。推荐 push、发布、建卡等出仓动作前，
必须先核实并写明受众与可见性（public/private、谁会看到）。

### Incident / Blocked

必须写：症状、当前影响、已查事实、实测结论、建议方案，以及为了排查已经做了什么、
明确没有做什么。超时/挂死类补充两次执行与推荐，不能只报“又超时了”。没有信息增量时
不得重复上报同一障碍。

### Done / Ack

必须写：outcome 是否成立、主要交付及用户可见影响、门禁读数、未验证面/残余风险，
以及请求的明确 ack。只有确需 owner 亲自验产品表现或高风险证据时才加“值得看”。
merge/push 回执另带 commit、冲突处置与回滚点。

## 质量门槛

- 结论范围不得超过证据范围；推断必须标明；
- 不贴过程流水账、完整文件清单或整屏命令输出；只解释它们对 outcome 的意义；
- 禁止以链接、路径或文件名代替完成内容和发现；证据默认最多两个引用，更多留在真源；
- “值得看”默认省略；出现时必须说明需要 owner 亲自判断什么，不能只是推荐阅读；
- “需拍板”不得裸写“等你决定”，也不得把尚未调查的不确定性外包给 owner；
- 外部依赖不得写成 pair 的当前任务；必须区分 `dependency parked` 与 `pair released`，
  并让 owner 一眼看出该 pair 是否可调度；
- 同一事件的更新必须指出“新在哪里”；没有新增事实就保持静默。

## 试行验收

1. owner 因“做了什么 / 当前什么状态 / 要我决定什么”而产生的澄清回合数为 0；
2. 删除汇报中的所有链接后，owner 仍能在 30 秒内理解局面并完成当下决策；
3. 汇报频率不高于本协议生效前的既有事件频率；
4. B/E 各在下一次 Done 复盘时裁定：转正、修订或撤销。
