# Owner 汇报协议

> 🧪 2026-08-17 起试行。复核点：B/E 两个现役 pair 各完成下一次 batch Done 后。
> 目标不是增加汇报频率，而是让 owner 用一屏看懂进展、发现、注意点与待决事项。

## 与 peer 门铃的边界

- **peer 门铃**只负责唤醒和路由：路径、轮次、verdict；不复制工件内容；
- **owner 汇报**负责信息压缩和注意力路由：是已提交工件的摘要投影，不是第二真源；
- 汇报正文由 agent 在当前 turn 末尾输出；system notification 只提醒事件和真源路径，不能替代正文；
- 仍然事件驱动：只在既有 milestone、gate、incident、Done 或 owner 主动询问时汇报，
  不新增 heartbeat、定时 ping 或 orchestrator 常驻；
- 汇报中的状态、读数、commit 和判断必须能回链到工作仓真源。

## 通用格式

```text
【<batch>｜<一句话状态>】

结论：当前结果、所处阶段，以及是否按计划推进。
完成：本轮最重要的 1～3 项；不枚举全部文件。
发现：新事实、风险或与原计划不同之处；没有则写“无新增风险”。
值得看：最多 1～3 个路径/页面，每项说明为什么值得看；没有则写“无”。
需拍板：无；或一句话题面 + 选项代价 + 推荐，并说明阻塞/不阻塞什么。
下一步：承担者 + 动作 + 下一次交棒或完成条件。
证据：commit、关键门禁读数、真源路径；只放支撑结论的最小集合。
```

首屏必须自含；详细证据留在链接工件里。字段可以合并成短段，但不得省略“需拍板”和
“下一步”。首次出现 batch、finding、watchlist 等编号时，必须跟一句人话自述。

## 四类变体

### Milestone / 旁观通报

结论先说阶段是否完成；完成、发现、下一步为必填。无需 owner 动作时明确写“需拍板：无”，
不得用疑问句把执行权递回 owner。

### Decision / Gate

开头三项依次是：①一句话说清拍什么；②选项、代价与推荐；③阻塞项与非阻塞项。
owner 应能只回 `A`、`B`、`ack` 或一句修正意见。推荐 push、发布、建卡等出仓动作前，
必须先核实并写明受众与可见性（public/private、谁会看到）。

### Incident / Blocked

必须写：症状、当前影响、已查事实、实测结论、建议方案，以及为了排查已经做了什么、
明确没有做什么。没有信息增量时不得重复上报同一障碍。

### Done / Ack

必须写：outcome 是否成立、主要交付、门禁读数、未验证面/残余风险、最值得 owner 看的一处，
以及请求的明确 ack。merge/push 回执另带 commit、冲突处置与回滚点。

## 质量门槛

- 结论范围不得超过证据范围；推断必须标明；
- 不贴过程流水账、完整文件清单或整屏命令输出；只解释它们对 outcome 的意义；
- “值得看”是注意力推荐，不是链接仓库；每个链接都回答“为什么看”；
- “需拍板”不得裸写“等你决定”，也不得把尚未调查的不确定性外包给 owner；
- 同一事件的更新必须指出“新在哪里”；没有新增事实就保持静默。

## 试行验收

1. owner 因“做了什么 / 当前什么状态 / 要我决定什么”而产生的澄清回合数为 0；
2. owner 不打开详细工件，也能在 30 秒内理解局面并决定是否深挖；
3. 汇报频率不高于本协议生效前的既有事件频率；
4. B/E 各在下一次 Done 复盘时裁定：转正、修订或撤销。
